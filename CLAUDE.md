# Reglas para Claude en este repo (web de Casa Tomás)

Proceso completo y guía práctica: [docs/PROCESO-DE-CAMBIOS.md](docs/PROCESO-DE-CAMBIOS.md). Obligatorio:

- **Ramas.** Cada cambio en su rama `feature/<tema>` o `fix/<tema>` (desde `staging`), con PR a `staging`; fusiónalo hacia `staging` con merge commit para verlo en la demo. **Nunca** hagas push a `main`, nunca fusiones un PR hacia `main`, nunca `push --force`. Producción solo cambia cuando el dueño acepta en GitHub un PR `release/X.Y.Z → main`.
- **Releases.** Solo con lo que pida el dueño: `node scripts/release.mjs pendientes`, luego `preparar '#PR' <sha> … --objetivo "…"` (primero con `--simular`), `git push -u origin release/X.Y.Z` y PR a `main` con la descripción de `node scripts/release.mjs informe --head release/X.Y.Z`. Si se bloquea por dependencias o conflictos, explícaselo al dueño: **no** añadas cambios ni uses `--no-depende` sin su «sí».
- **Commits:** `git -c user.name=Claude -c user.email=noreply@anthropic.com commit …` (el plan Hobby de Vercel bloquea los commits de autores con cuenta de Vercel que no son del equipo). Tipo convencional (`feat(…)`, `fix(…)`…) y, si cambia un comportamiento, líneas `Antes: …` / `Ahora: …` en el cuerpo. Para `preparar`, exporta `RELEASE_GIT_NAME=Claude RELEASE_GIT_EMAIL=noreply@anthropic.com`.
- **Antes de subir:** `npm test` en verde, y `npm run test:e2e` si tocas reservas, carta, cheques o maquetación (ver `.github/workflows/ci.yml`). En una release, los mismos tests sobre la rama `release/X.Y.Z`.
- **Supabase (funciones de `supabase/functions/`):** se despliegan primero en la demo, `SUPABASE_ACCESS_TOKEN="$SUPABASE_ACCESS_TOKEN_DEMO" npx supabase functions deploy <función> --project-ref sfonaclosuafvlhutkon` (tokens y accesos: `.claude/becarios/reference/accesos.md`). En producción, `haqmmdfdzzatdnrrcgez`, **solo** después de que el dueño acepte el PR de la release y lo pida explícitamente. El proyecto viejo `jeamoczmbfsnwkfjxcyo` no se toca. Las migraciones viven en el repo del panel.
- **Después de subir:** a `staging`, comprueba que Vercel publica la demo (READY) y dile al dueño qué probar; a `release/X.Y.Z`, que la preview de la candidata está READY y sirve esa versión (`node scripts/comprobar-despliegue.mjs <url> --version X.Y.Z --commit <sha>`), y dale la URL del PR y de la preview.
- **Versión:** `X.Y.Z` en `versionado.json` y entrada en `CHANGELOG.md`; los escribe solo `scripts/release.mjs`. No los edites a mano.
